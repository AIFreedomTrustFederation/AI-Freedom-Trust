A person, family, trust, community, repository, model, service, or agent can participate without surrendering its center. The shared pattern is inherited through local-first trust seeds, identity and mission structures, governance rules, provenance, evidence, and explicit consent. It does not acquire moral authority merely because it can complete a task. Decisions involving identity, money, custody, publication, legal effect, secrets, private data, safety, or irreversible change return to the person or governed body from which authority came.

## Book III — SOP-ALOHA-001 in the Doctrine Repository

The canonical loop is:

```text
Receive → Inspect → Name → Propose → Consent → Act → Verify → Record → Return
```

Here, **Receive** means preserving source material and authorship before interpretation. **Inspect** means checking the actual document, data, build source, citations, and repository state. **Name** means separating doctrine, empirical evidence, engineering claims, symbolic language, and unresolved questions without fragmenting the prose into editorial commentary. **Propose** means AI may synthesize or rewrite while remaining distinguishable from authorial authority. **Consent** protects constitutional meaning, authorship, publication, and high-impact claims. **Act** changes the source of truth rather than merely describing a hypothetical correction. **Verify** means documents build, links resolve, research reproduces where claimed, and rendered editions remain legible. **Record** is carried by Git history, research outputs, provenance, and publication artifacts. **Return** closes the loop in finished language that a reader can inhabit without reading the history of how it was corrected.

### Local trust-seed bootstrap and validation boundary

The checked-in [`scripts/create_trust_seed.py`](scripts/create_trust_seed.py) creates a **private-by-default local draft**, not a verified public identity or an automatically federated node. From the repository root, use a new relative destination directory:

```bash
python scripts/create_trust_seed.py my-local-trust
python scripts/validate_doctrine.py
python -m unittest discover -s tests -v
```

The generator validates the canonical template's expected files and manifest fields, rejects symlinked or executable template entries and unsafe destination paths, refuses to overwrite an existing destination, and stages output before moving it into place. The generated manifest retains local-private defaults, disables public federation linking, and requires human approval for AI stewardship. The steward must review the resulting documents and explicitly authorize any later sharing or publication.

**Cryptographic identity and provenance are not established by this bootstrap.** The current `IDENTITY.md` describes local claims and distinguishes them from verified credentials; the root `scripts/init_trust_identity.py`, `scripts/sign_trust_seed.py`, and `scripts/verify_trust_seed.py` are not present on the checked default branch. Do not infer that signing or signature verification is available from proposed changes or unmerged pull requests. For validation scope and empirical/PDF limitations, see [`docs/validation.md`](docs/validation.md).

The checked-in [workspace metadata](aift.repo.json) declares `verify` as `git status --short`, which reports working-tree changes but does not run the doctrine validator or unit tests. It also declares `pull` as `git pull --ff-only`, a potentially mutating Git operation. Separately, the [capability registry](.aift/capabilities.json) marks `sync` as `ready` with the descriptor `git remote/status`, while the only checked-in [AIFT command script](.aift/commands/status.sh) reports repository status. There is no standalone synchronization script under `.aift/commands/`. These declarations do not prove that synchronization occurred, that validation passed, or that a Git mutation was authorized. Use the explicit validation commands above and inspect their results; publication work also requires build and visual inspection when a rendered document changes.

### BookForge PDF preview and publication boundary

The checked-in [BookForge Scroll PDF workflow](.github/workflows/bookforge-scroll.yml) runs on pull requests that change `latex/**` or the workflow itself, and on manual dispatch. It compiles [the Scroll LaTeX source](latex/documents/one-eternal-scroll-of-aloha.tex) twice with XeLaTeX and uploads a PDF and build log as a **workflow preview artifact**. This job does **not** promote the preview into [`docs/pdf/`](docs/pdf/), update the public reading edition, or verify that the linked [Scroll PDF](docs/pdf/one-eternal-scroll-of-aloha.pdf) matches the latest source. A successful build establishes compilation for that run, not editorial, visual, citation, or publication approval.

The preview workflow references `actions/checkout@v4` and `actions/upload-artifact@v4` by mutable major-version tags and installs XeLaTeX packages without pinned package versions. Therefore a passing preview does not establish a byte-for-byte reproducible toolchain or independently attested artifact provenance. Record the workflow run, source commit SHA, and artifact checksum when comparing builds; these records support traceability but do not substitute for author approval.

For a controlled local publication, [the PowerShell LaTeX builder](scripts/build-latex.ps1) copies successfully generated PDFs into `docs/pdf/` after two XeLaTeX passes. The steward must review the rendered pages, verify the intended source revision and links, and explicitly commit the approved artifact; see the [validation guidance](docs/validation.md). Neither preview CI nor a tracked PDF alone establishes independent review or cryptographic publication provenance.
